# CAPTURE scope and execution

Design authority: [MAIN/CAPTURE execution spec](../../../../docs/superpowers/specs/2026-09-17-main-capture-execution-design.md), sections 5–9.

This directory is the destination for CAPTURE extraction. Current entry points remain `../../prototype_runtime.py` for frame setup/evaluation/resume, `../../capture_evaluation.py` for coordinator tickets and cleanup, and `../../runtime_api.py` for public values and namespace settlement. No `CaptureScope` or `CaptureExecutor` implementation is implied by this guidance.

- The controller creates one `CaptureScope` per recognized stop before staged setup. Multiple CAPTURE cells share that scope and each receive a separate operation ticket. The scope owns identity evidence, setup readiness, dirty-root/writeback ledger and resource leases; it does not duplicate the arbiter's pending protocol capability.
- `CaptureCellPolicy` owns lowering profile, capture namespace access, dirty roots, message/Worker binding and reply settlement. `CaptureExecutor` owns evaluation, inspection, materialization/transfer, cleanup and resume sequencing through the arbiter port. These components depend on execution contracts and typed ports, not a concrete controller or `RdbgSession`.
- Revalidate remote frame identity and the local route fence before dispatch. An unchanged location after ambiguous Continue is insufficient evidence of the same stopped frame. Pending or unknown evaluation blocks dependent requests until settlement or confirmed teardown; it does not block read-only status or independent Python execution.
- A confirmed BSL, Worker, inspection or materialization failure ends that request without proving frame loss. Track cleanup/pin/breakpoint debts separately and block the affected capabilities. Setup failures retain known identity evidence and readiness progress; do not manufacture a second mutable CAPTURE lifecycle in the API.
- Root writeback happens only during resume. Record confirmed, failed and unknown root writes separately; never blindly repeat an unknown write or Continue. CAPTURE is not a transaction: confirmed partial writes and arbitrary BSL side effects cannot be rolled back by restoring Python state.
- The owner retains pending evaluation and cleanup duties after waiter detachment. User Stop after dispatch requests actual remote termination; no cancellation success or preserved frame may be claimed without evidence. There is no BSL execution deadline, though individual network requests remain bounded.

Target contracts are `PreparationContext`/`PreparedCell`, `CellPolicy`, the CAPTURE capability port and arbiter tickets/fences. Preserve current `CaptureFence`, `CaptureStatus`, evaluation/resume ticket and public `CaptureView` compatibility while their ownership migrates. `CaptureEvaluationCoordinator` is transitional and must ultimately yield queue/ticket ownership to the common arbiter; renaming it to an executor does not perform that migration.

Focused checks: `tests/unit/test_capture_evaluation_lifecycle.py`, `test_capture_control_plane.py`, `test_capture_resume_lifecycle.py`, `test_capture_materialization_lifecycle.py`, `test_capture_context_views.py` and `test_runtime_api.py`. Cover failure followed by another request in the same confirmed frame, pending ownership, partial/unknown resume and stale fences. Live error → retry → materialization → variables → resume qualification requires opt-in 1C tests on a temporary infobase.
