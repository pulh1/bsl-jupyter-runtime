# CAPTURE scope and execution

Design authority: [MAIN/CAPTURE execution spec](../../../../docs/superpowers/specs/2026-09-17-main-capture-execution-design.md), sections 5–9.

`scope.py` records one recognized stop, frame/setup evidence, dirty roots, writeback ledger, temporary cleanup debts and release. `executor.py` performs ordered stop setup; `cell_evaluator.py` and `operation_executor.py` execute a cell; `inspection.py`, `materialization.py`, `writeback.py` and `stack.py` own their focused CAPTURE capabilities. `policy.py` and `preparation.py` select CAPTURE lowering. `execution/controller/controller.py` composes most of these through one arbiter in component tests. The public path still uses `../../prototype_runtime.py`, `../../capture_evaluation.py` and `../../runtime_api.py`.

- The controller creates one `CaptureScope` per recognized stop before staged setup. Multiple CAPTURE cells share that scope. The scope owns identity, setup evidence, dirty-root/writeback state and temporary-key debts; Worker pin ownership remains migration work. It must not duplicate the arbiter's pending protocol capability. A confirmed temporary-key deletion failure can be retried by `submit_capture_cleanup_retry` without repeating admission or payload; an unknown deletion outcome needs reconciliation first. Neither fact alone loses the frame.
- `CaptureCellPreparer` and `CaptureCellPolicy` own the lowering profile, message key, dirty roots and route-specific preparation/settlement contracts. Public namespace and Worker binding are not yet wired. The component controller runs setup, cell eval, variable reads, materialization, temporary cleanup retry, dirty-root writeback and resume through the arbiter port. `CaptureSetupAdapter` and `CaptureCellEvaluator` use bounded transport intervals without a BSL execution deadline. Stack inventory reads the saved stop and uses the existing public `LocalStackAdapter` for masking, but runtime wiring is still pending.
- Revalidate remote frame identity and the local route fence before dispatch. An unchanged location after ambiguous Continue is insufficient evidence of the same stopped frame. Pending or unknown evaluation blocks dependent requests until settlement or confirmed teardown; it does not block read-only status or independent Python execution.
- A confirmed BSL, Worker, inspection or materialization failure ends that request without proving frame loss. Track cleanup/pin/breakpoint debts separately and block the affected capabilities. Setup failures retain known identity evidence and readiness progress; do not manufacture a second mutable CAPTURE lifecycle in the API.
- Root writeback happens only during resume. Record confirmed, failed and unknown root writes separately; never blindly repeat an unknown write or Continue. CAPTURE is not a transaction: confirmed partial writes and arbitrary BSL side effects cannot be rolled back by restoring Python state.
- The owner retains pending evaluation and cleanup duties after waiter detachment. User Stop after dispatch requests actual remote termination; no cancellation success or preserved frame may be claimed without evidence. There is no BSL execution deadline, though individual network requests remain bounded.

Target contracts are `PreparationContext`/`PreparedCell`, `CellPolicy`, the CAPTURE capability port and arbiter tickets/fences. Preserve current `CaptureFence`, `CaptureStatus`, evaluation/resume ticket and public `CaptureView` compatibility while their ownership migrates. `CaptureEvaluationCoordinator` remains transitional and must yield queue/ticket ownership to the common arbiter. A confirmed setup failure now reports `capture_setup_failed` with stage evidence; admission remains blocked because RDBG has no remote stop nonce that can rule out an external Continue and repeat stop at the same location. A safe retry needs stronger same-stop evidence.

Focused component checks: `tests/unit/test_capture_stop_recovery_component.py`, `test_capture_stack_inventory_adapter.py`, `test_capture_materialization_executor.py`, `test_capture_inspection_executor.py`, `test_capture_writeback_executor.py`, `test_capture_scope.py` and `test_execution_controller_routes.py`. Public regression checks remain `test_capture_evaluation_lifecycle.py`, `test_capture_control_plane.py`, `test_capture_resume_lifecycle.py`, `test_capture_context_views.py` and `test_runtime_api.py`. Live error → retry → materialization → variables → resume qualification requires opt-in 1C tests on a temporary infobase.
