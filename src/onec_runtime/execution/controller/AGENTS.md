# Route selection and admission

Design authority: [MAIN/CAPTURE execution spec](../../../../docs/superpowers/specs/2026-09-17-main-capture-execution-design.md), sections 3–6 and 10.

`controller.py` owns one `MainOperation`, current `CaptureScope`, route handoff and admission for MAIN/CAPTURE/inspection/materialization/resume. Public `RuntimeSession.start()` composes this controller through `../post_bootstrap.py` and exposes it through `PublicExecutionFacade`. `stop_coordinator.py` owns ticket Stop observation; it never reads RDBG events.

- `RuntimeSession` provides MAIN/CAPTURE policy/executor route bindings, arbiter and service ports. The controller retains the current `MainOperation` and `CaptureScope`; it does not construct a new executor for each cell.
- Create one `MainOperation` at accepted MAIN admission, and one `CaptureScope` at each recognized capture stop before setup. Validate command identity at capture entry and completion. A MAIN command survives its CAPTURE stops; a cell reply or loss of a single frame does not establish command completion or target loss.
- Expose stable preparation context only for MAIN ready or confirmed CAPTURE idle. `await_preparation_context`, `validate_preparation` and `submit_cell` are the target port boundaries. Tokens are opaque to callers; each preparation gets its own nonce. Validate owner/fence, context revision and namespace/Worker guards before acceptance and arrange revalidation before side effects. The controller calls version-owner ports rather than storing a second mutable catalog.
- Stop routing and admission belong here. Policies lower cells and settle replies; route-specific services build expressions and execute RDBG work. The controller composes those services and orders CAPTURE setup, writeback, cleanup and Continue through their ports. Return results through typed outcomes/callback ports; executors must not import this concrete controller.
- `capture_private_data_plane.py` owns selected-table descriptor recipes and builds manager metadata, materialization and confirmed cleanup-retry worker plans. The controller holds the lock, validates the exact CAPTURE stop, reserves and retires ledger records, submits direct tickets and observes Stop; the data-plane service has no arbiter or lifecycle lock.
- `submit_resume` owns one fenced transaction for optional successor breakpoints, explicit dirty roots, writeback, context cleanup and Continue. Successor workspace installation precedes writeback; publish the next local registry only on confirmed installation. A frozen writeback ledger accepts no new roots on retry. Worker activation binding is a one-time idle composition step; it must not race admission.
- Do not add a second MAIN/CAPTURE phase enum. Derive readiness/status from operation/scope evidence and resource debts. A failed request, waiter detachment, transport interval timeout or recovery checkpoint alone cannot prove frame or target loss. A nonterminal MAIN operation prevents replacement admission regardless of the last cell reply.
- One arbiter serializes runtime RDBG and event reading. Controller routing updates must respect that ownership; mailbox/state locks must not cover transport, user callbacks or waiting for results. Unknown dispatch/Continue remains owned until reconciled, without blind retry or activation of a replacement runtime.
- `worker_mutation_route()` admits helpers only at a free MAIN service stop or a confirmed ready CAPTURE stop, with no continuation admission. Worker publication then rechecks this route and the arbiter token inside its ticket. `StopCoordinator` observes the ticket mailbox; only confirmed termination of the exact target marks MAIN or CAPTURE lost.
- Direct RDBG tickets use `SubmissionReceipt` in the same arbiter mailbox admission as queue insertion. If the initiating call is interrupted before it returns the ticket, cancel an unstarted ticket or request Stop for an active one. Retire CAPTURE ledger reservations only when cancellation before remote effect is proven.
- For a confirmed CAPTURE result or local rejection, settle its public evaluation ledger on the arbiter worker before the ticket wakes its synchronous caller. The background ticket observer handles unknown outcomes and exceptional bypass paths; do not make a confirmed `to_df()`, completion or cell failure depend on observer scheduling.

Derive lifecycle from `MainOperation`, `CaptureScope`, arbiter tickets and exact target evidence. Do not add a second owner for a pending RDBG operation.
